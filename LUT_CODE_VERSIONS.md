# ORAC LUT code versions, releases and provenance

This document is the central record of how the LUT generator's source code
is versioned, which Git revision produced each generation of lookup tables,
how a historical release is recovered and inspected, how a new release is
made, and how a LUT is traced back to the code that generated it.  It
complements `LUT_FORMAT_CONTRACT.md` (NetCDF attribute contract) and the
production notes `runs/V24_PRODUCTION.md` and `runs/V25_PRODUCTION.md`.

## 1. Three different things called "version"

| Quantity | Where it is defined | Example | Meaning |
|---|---|---|---|
| **LUT product version** | run file `version = N`; product name `_vNN.nc` | 25 | A product set: its grids and the scientific scheme it was produced with.  ORAC users select tables by it. |
| **Source-code release** | `CODE_VERSION`, `code_release`; annotated Git tag | `lut-code-v25`, `lut-code-v25.1` | An immutable, tagged state of this repository.  Several releases may produce the same product version (a maintenance release keeps `lut_version` and gets a new tag such as `lut-code-v25.1`). |
| **Git commit** | `git rev-parse HEAD` | `f066fdd…` | The exact source.  A release tag names one commit; a working tree can also be at a commit after the tag, or modified. |

Two further pieces of state complete the identification: the **working-tree
status** (`CLEAN` or `MODIFIED`, from `git status`; a modified tree never
identifies itself as the official release) and the **scientific
configuration** (`CODE_VERSION`, `scientific_config`, with the numerical
options recorded per product in its provenance file).

`CODE_VERSION` is the single authoritative definition; nothing else in the
source carries a hard-coded release number.  Its fields:

```
code_release = lut-code-v25.1          # the annotated tag of this release
lut_version = 25                       # the product version it produces
compatible_lut_versions = 24           # others it may produce (justified below)
scientific_config = v25
scientific_config_description = ...    # one line
```

## 2. What the generator does with it

At start-up every entry point (`create_orac_luts.py runs/x.run`, `python -m
oraclut.generate`, and therefore every SLURM job through
`scripts/run_oraclut_lut.slurm`) prints

```
ORAC LUT Generator
------------------------------------------------------------
Generator:         create_orac_luts.py (run file)
LUT version:       25 (requested 25)
Code release:      lut-code-v25.1
Git commit:        1a2b3c4 (1a2b3c4…full hash…)
Git describe:      lut-code-v25.1-0-g1a2b3c4
Release tag:       HEAD is the tagged release lut-code-v25.1
Working tree:      CLEAN
Scientific config: v25
                   V24 numerics (...) plus the V25 cloud vertical temperature profiles ...
Compatible LUTs:   24
------------------------------------------------------------
```

A modified tree prints `Working tree:      MODIFIED` followed by the modified
and untracked production files; a tree at a later commit prints `HEAD is N
commit(s) after tag …`; without Git metadata the banner says so
(`Git commit: unavailable`, `Working tree: UNKNOWN (Git metadata unavailable:
…)`) rather than inventing an identifier.

**Consistency check.**  Before any Mie or DISORT work the generator compares
the requested LUT version (run file `version`, or `--version` of
`oraclut.generate`) with `CODE_VERSION`.  Only `lut_version` and the listed
`compatible_lut_versions` are accepted; anything else stops the run with

```
create_orac_luts.py: run file runs/x.run requests LUT version 22, but this
source release lut-code-v25.1 produces LUT version 25 (compatible: 24). ...
```

The output filename is never adjusted to hide a mismatch, and the code version
is never inferred from a filename.  The only compatibility mechanism is the
explicit `compatible_lut_versions` list.  For `lut-code-v25.x` it contains 24
because the V25 code with `cloud_vertical_profile` absent or `'isothermal'`
performs the V24 calculation (`create_orac_luts.py`, "Versions and numerical
changes", item 5); the V24 products themselves were generated by
`lut-code-v24`, which remains the reference for them.

**Provenance.**  Every product is written together with a sidecar
`<product>.provenance.json` (`x_v25.nc` -> `x_v25.provenance.json`,
`src/oraclut/provenance.py`) containing: LUT version; `code_release`,
`scientific_config`; full Git commit, `git describe`, branch, working-tree
status with the list of modified/untracked production files; UTC generation
time; host, user and SLURM job identifiers; platform, instrument, particle
model, forward model, channels, SRF files; the run/configuration file (path,
SHA-256 and verbatim text) and the instrument, microphysics, LUT-definition
and atmosphere files (paths and SHA-256); the grid (every axis with its
spacing and values); the numerical settings (radius-integration scheme, Mie
radius limits, Legendre scheme / nmom, SRF quadrature, cache reuse); the
radiative-transfer settings (DISORT streams, Rayleigh, gas, atmosphere, cloud
vertical profile and its attributes); software versions (Python, NumPy,
netCDF4, libnetcdf, HDF5, Fortran compiler and flags); and the SHA-256 and
size of the product.  The NetCDF product itself is unchanged by this: no
dimension, variable, attribute or value is added.

Historical products (V21-V25) have no sidecar.  Their provenance is the
reconstruction in section 3, marked as such; nothing is written next to them.

## 4. Everyday commands

All commands run from the repository root on an AOPP interactive host
(`atmlxint1/2/3/5/6`), with `PYTHONPATH=src` where `python -m` is used
(`create_orac_luts.py` sets it itself).

```
# Current code version, commit and working-tree status (the start-up banner)
PYTHONPATH=src python -m oraclut.version
PYTHONPATH=src python -m oraclut.version --json        # machine-readable

# Is the tree modified?  (exit status 0 = clean)
git status --porcelain --untracked-files=all | grep -q . && echo MODIFIED || echo CLEAN

# Historical LUT code releases
PYTHONPATH=src python -m oraclut.version --list-releases
git tag -n9 -l 'lut-code-v*'

# Inspect an old release safely (a temporary worktree; the production tree is untouched)
git worktree add --detach /network/scratch/$USER/oraclut-worktrees/lut-code-v22 lut-code-v22
(cd /network/scratch/$USER/oraclut-worktrees/lut-code-v22 && PYTHONPATH=src python create_orac_luts.py runs/<run>.run)
git worktree remove /network/scratch/$USER/oraclut-worktrees/lut-code-v22   # when finished

# Restore the current production version in the main tree (after inspecting elsewhere)
git switch main && git status

# Which code generated a particular output?
PYTHONPATH=src python -m oraclut.version --verify <product>.provenance.json [--lut <product>.nc]
#   -> commit present in this repository, release tags at / containing it,
#      working tree CLEAN or MODIFIED at generation time, product SHA-256 match
```

A worktree at a historical release needs its Fortran kernels built on first
use (`build/` is not versioned; `src/oraclut/optics/legacy_mie.py` and
`src/oraclut/radiative_transfer/legacy_disort.py` build them automatically
with `gfortran`, GNU Fortran 12.2.0 on the AOPP hosts) and does not contain
the git-ignored Baum tables (`create_orac_lut/input_files/baum/`), which the
ice `agg/ghm/src` models need; copy or link them from the production tree.

## 5. Making a new release

1. Develop and test in the working repository (`main`).  Validate the
   scientific change (`validation/`, tests, comparison with the previous
   release).
2. Update `CODE_VERSION`: `code_release` to the new tag name (`lut-code-v26`
   for a new product version; `lut-code-v25.2` for a maintenance release
   that keeps `lut_version`), `lut_version`, `compatible_lut_versions` (each
   entry justified in section 2 of this document), `scientific_config` and
   its description.  Record the new version in section 3 above and, for a new
   product version, in `create_orac_luts.py` ("Versions and numerical
   changes") and a `runs/V<nn>_PRODUCTION.md`.
3. Commit the definitive source on `main` (`git add` the specific files; no
   generated LUTs, backups or caches).
4. Tag: `scripts/tag_lut_code_release.sh` checks that the tree is clean, that
   HEAD is on `main`, that `CODE_VERSION` names the requested tag and that
   the tag does not exist, then creates the annotated tag with a message
   describing the release.
5. Push: `git push origin main && git push origin <tag>`; verify with
   `git ls-remote origin refs/heads/main 'refs/tags/lut-code-v*'`.
6. Generate the tables from that release (the production submit scripts
   already refuse a modified tree or a HEAD not contained in `origin/main`);
   every job prints the banner and writes a provenance sidecar next to each
   product.
7. Keep the sidecars with the products (same directory); `python -m
   oraclut.version --verify` relates them to the repository later.

Rules: one definitive branch (`main`); no permanent experimental branches or
duplicated source trees; historical implementations are recovered through
their tags into temporary worktrees; tags are never moved or deleted once
pushed; history is never rewritten.

## 6. Restoring V22 as the production implementation

The intended operation is an ordinary commit on `main` that brings the
scientific files back to their `lut-code-v22` (`9d663e9`) content while
keeping the history, the later infrastructure (NetCDF NC_STRING writer and
repair, versioning, provenance) and the V23-V25 material recoverable through
their tags.  The procedure, the exact file list and the validation of the
recovered V22 code are set out in
`validation/v22_recovery/REPORT_v22_recovery.md`; it is executed only after
explicit approval.  After restoration `CODE_VERSION` declares a new
maintenance release of the V22 science (for example `code_release =
lut-code-v22.1`, `lut_version = 22`), never the historical tag itself,
because the restored tree is not byte-identical to `9d663e9`.
